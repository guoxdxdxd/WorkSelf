# WorkSelf · 工作助手

> 给 AI 一个真实可用的工作环境：项目、事项依赖、人物经验都能一键进对话，结论再写回档案。

WorkSelf 是 [DeepSeek Harness](https://github.com/deepseek-ai) 的本地插件。它不把桌面任务管理器搬进对话，而是把「你正在做的事」整理成 AI 能读懂、能追问、能沉淀的上下文：

- **能建模**：项目有目标、硬节点、背景、进展；事项有负责人、涉及人员、依赖、到期、日志；每个人带「打交道经验」。
- **能进对话**：在项目、事项、日志或联系人上点「加入对话」，输入框出现一条带 uid / item / path 的【工作上下文】，AI 先展开档案再回答。
- **能沉淀**：每轮对话后，AI 判断归属（项目事项还是日常工作），把事实、决定、状态变化、他人反馈写成日志，把新联系人补进名单，把经验写回 Markdown。

一句话：**上下文进得去，结论写得回。**

## 它解决什么

普通任务管理器回答「还有哪些事」；WorkSelf 想回答的是另一个问题：**这件事卡在哪、该找谁、怎么开口、下一步做什么。**

所以档案里没有日历和甘特图，只有和「让 AI 理解并推进工作」直接相关的四面：

| 页签 | 内容 |
| --- | --- |
| 工作台 | 在办、逾期、阻塞、最近日志、日常工作；每条都能加入对话 |
| 项目 | 目标与背景、事项列表（全部 / 未完成快筛）、项目汇报；项目与事项都能加入对话 |
| 联系人 | 资料 + 打交道经验；可加入对话 |
| 设置 | 目录、索引、迁移旧档案（单文件 → 文件夹） |

## 安装

前提：一份带客户端插件能力的 DSH（DeepSeek Harness）。仓库根就是插件包，以下三种方式任选其一。

### 从 npm 安装（推荐）

在 DSH 侧栏打开 **Plugins** → **Add plugin** → **Install a third-party plugin**，填包名：

```text
workself
```

装好后按提示**重启 DSH**（宿主侧插件不热更）。

### 从 GitHub 安装

不想用 npm 时，填仓库地址也可以：

```text
github:guoxdxdxd/WorkSelf
```

### 本地开发（改代码用）

把仓库根以本地 link 方式挂到 DSH profile（默认 `~/.dsh/profiles/desktop/`）：

1. 在 profile 的 `package.json` 依赖里加一行（路径换成你本机的仓库根）：

   ```json
   "dependencies": {
     "workself": "link:/path/to/WorkSelf"
   }
   ```

2. 在同一个文件的 `dsh.profile.bundles` 里追加 `"workself"`。
3. 在 profile 目录执行 `pnpm install`，把软链装到 `node_modules/workself`。
4. **重启 DSH**。

打开任意会话，右侧栏开始页会出现工具卡片「工作驾驶舱」。首次打开时插件会在当前工作区：

- 创建 `workos/` 档案（已有文件不覆盖）；
- 在联系人里加入默认的「我」，新事项负责人默认「我」；
- 在工作区根目录写入 `AGENTS.md` 的助手设定段（已有内容保留，插件升级时原地刷新）。

## 用法

### 归档与日志

AI 每轮先判断归属：一次性的、没有独立项目目标 / 节点 / 交付物的临时事 → **日常工作**（`workos/work/{部门}/{年}/日常工作/`）；有独立目标、交付物、节点或需持续跟进的事 → 先找项目，能挂现有事项就更新，没有就补建。

日志一条对应一次变更：前因 → 事件 → 结果与下一步 → 关联。同一天同一件事合并成一条，补充细节改原条目，不写流水账。

### 日常工作日

不属于任何项目的事项不硬塞进项目：顶部「添加事项」的弹窗比项目内新增多一个「所属项目」下拉，留空即落到 `日常工作/`，一个事项一个文件，文件名前缀为添加时的日期时分秒，事项 id 为 `d1`、`d2`…。个人汇报会把它们一起汇总。

### 日报 / 周报

汇报分两个口径，写在两个地方：

- **个人汇报**：汇总全部项目与日常工作，写回 `workos/data/日报/YYYY-MM-DD.md`、`workos/data/周报/起始_结束.md`。
- **项目汇报**：只汇总当前项目，写回该项目文件夹的 `汇报/日报/`、`汇报/周报/`，与 `事项/` 平级。

生成方式两种都支持：

- **手动**：选一天或一个时间段 → 确认后新开对话，助手用 `workos_report_data` 取数，写成含生成时间、汇报时段、简介、详细内容的汇报，再用 `workos_report_save` 写回。
- **自动**：同一弹窗的「自动生成」页签选频率（每天 / 每周五 / 每周一）、时间、内容（当天日报 / 本周周报 / 上周周报），向 DSH 添加自动化任务；到点自动在专用对话里生成并写回。

### 工作区 Agent

首次打开会在工作区根目录生成 `AGENTS.md`（助手段用 `<!-- workos-agent:start -->` 标记）：

- 以「我」的身份回答，先读 `workos/data/个人信息.md`；
- 看到【工作上下文】先 `workos_context`，再查依赖与相关人的打交道经验；
- 每轮自动判断归属并写回日志；新出现的人先问清资料再 `contact.add`；
- 回答结构：判断 → 动作（谁 / 何时 / 怎么说）→ 风险 → 检查点。

DSH 的 `dsh-agent-instructions` 会在该工作区的每个会话里自动加载这份文件，不需要手动选 agent。文件里其他内容不会被覆盖。

## 工具与技能

宿主侧注册 8 个工具：

| 工具 | 用途 |
| --- | --- |
| `workos_context` | 展开【工作上下文】：项目、事项、依赖、人员经验、日志（`uid=0` 为日常工作） |
| `workos_overview` | 全局：在办、逾期、阻塞、最近日志、日常工作 |
| `workos_query` | 结构查询 projects / items / logs / contacts |
| `workos_search` | 全档案全文检索（中文两字词可用） |
| `workos_read` | 读任意 Markdown 原文（日常工作可给 `itemId: d1`） |
| `workos_update` | 建项目、加 / 改 / 删事项、记日志、补经验、写回（不传 `uid` = 日常工作） |
| `workos_report_data` | 读取某时段日志、项目进展与在办事项，专供生成日报周报（传 `uid` 只取一个项目） |
| `workos_report_save` | 写回汇报：不传 `uid` 写 `data/日报|周报`（个人），传 `uid` 写项目文件夹的 `汇报/日报|周报` |

内置两个技能：

- `workos-persona`：带环境回答 + 写回（【工作上下文】的处理规则、日志写法、回答结构）。
- `workos-maintain`：信息维护（归属判断、日志去重、打交道经验与通用经验的沉淀）。

## 数据

**Markdown 是唯一真相**，全部放在当前工作区的 `workos/` 下：

```text
workos/
├── data/
│   ├── workos/contacts.md      联系人（含打交道经验）
│   ├── workos/meta.yaml        项目 uid 与类型
│   ├── workos/.index/          SQLite 检索索引（可删可重建）
│   ├── 日报/YYYY-MM-DD.md       个人日报
│   ├── 周报/起始_结束.md        个人周报
│   └── {个人信息,人脉关系,企业组织架构,当前企业信息,
│        年度目标与KPI,规章制度,常用资源,工作经历,经验}.md
└── work/{部门}/{年}/
    ├── 项目/{项目名}/
    │   ├── README.md              项目主档：元数据、目标与背景、事项索引、进展、复盘
    │   ├── 事项/w{编号} {事项名}.md  一个事项一个文件：字段、详情与日志
    │   └── 汇报/日报|周报/          项目汇报（只含该项目）
    └── 日常工作/
        └── YYYY-MM-DD HH-MM-SS {名称}.md
```

设计约束：

- 一个项目一个文件夹，项目再大也只在文件夹里生长；
- 一个事项一个文件，日志写在所属事项文件的 `## 日志` 里，不单独建 `log.md`；
- 不属于项目的事项放 `日常工作/`，不硬塞进项目，也不为它造项目；
- SQLite 只做检索，删掉不会丢数据。

完整字段与文件格式见 [`docs/DATA_MODEL.md`](docs/DATA_MODEL.md)。

`workos/`（真实工作档案）与 `AGENTS.md`（运行期生成）都在 `.gitignore` 里，不会被提交。

## 开发

- 插件是纯 ESM，无构建步骤；宿主侧用 Node 直接加载。改 `index.js` / `lib/*` 后需**重启 DSH**。
- 右栏界面在 `client.js`，由 DSH 打包进客户端；改界面时如果同时跑着 DSH 的 `pnpm run dev:web`，刷新页面即可看到，否则重新打包。
- 提交前至少做语法检查：

  ```bash
  for f in index.js client.js lib/*.js; do node --check "$f"; done
  ```


## 隐私

- 工作档案 `workos/`、工作区 `AGENTS.md` 不进版本库；仓库里只有插件代码与文档，不含截图。
- 数据只存在本机工作区里，插件不上传、不外发，也不做统计上报。
- 仓库不包含任何界面截图；文档里的示例数据统一用「示例展会」「张三 / 李四 / 王五」「某某集团」。
