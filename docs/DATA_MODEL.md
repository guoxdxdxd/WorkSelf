# 数据模型（workos/v2）：让 AI 读懂工作环境

## 目标决定结构

助手的价值在三个问题：**这件事卡在哪？该找谁、怎么说？下一步做什么？** 所以档案不是「任务清单」，而是：

- 项目：目标 + 硬节点 + 背景 + 进展 + 复盘
- 事项：名称、详情、状态、负责人、涉及人员、到期、**依赖**、**日志**
- 人：联系资料 + **打交道经验**（可累积）
- 经验：跨场景可复用的方法

Markdown 仍是唯一真相；SQLite 只是可删的检索索引。

## 项目文件夹

一个项目一个文件夹，项目再大也只在文件夹里生长：

```
work/{部门}/{年}/项目/{项目名}/
├── README.md              项目主档
└── 事项/
    ├── w1 {事项名}.md
    └── w2 {事项名}.md
```

### README.md（项目主档）

只放项目级信息。`## 工作事项` 是索引，不是数据源——事项的真实字段在各自的文件里。

```markdown
---
schema: workos/v2
kind: project
uid: 1001
dept: 市场部
year: 2026
status: doing
project_type: 展会
priority: 中
start: 2026-11-10
end: 2026-12-20
owner: 王五
participants:
  - 张三
  - 李四
goal: 12 月 20 日顺利开展
---

# 示例展会

## 目标与背景

市场部牵头，重点锁定展台设计与产品清单。

## 工作事项

| 事项 | 状态 | 负责人 | 到期 | 文件 |
| ---- | ---- | ------ | ---- | ---- |
| w1 确认展位信息 | 已完成 | 李四 | 2026-11-21 | 事项/w1 确认展位信息.md |
| w2 展台设计 · 初稿 | 进行中 | 张三 | 2026-11-28 | 事项/w2 展台设计 · 初稿.md |

## 项目进展

| 日期 | 进展 | 备注 |
| ---- | ---- | ---- |
| 2026-11-19 | 立项 | — |

## 复盘

- **好的地方**:
- **问题**:
- **下次改进**:
```

项目名取 README 的一级标题；界面里改项目名会同步重命名项目文件夹，并改写 `_年度概述.md` 里指向该项目的链接。负责人、涉及人员、类型、优先级、开始/关键节点、目标、背景都可在「编辑项目」里再次修改；`## 目标与背景` 的第一行是目标，其余是背景，写回时两者分开保存，不会重复。项目的负责人和涉及人员点击后进入对应的联系人编辑。

### 事项文件

一个事项一个文件。字段在前面的 frontmatter 里，正文是详情与日志；日志不单独建文件。

```markdown
---
schema: workos/v2
kind: item
uid: 1001
item_id: w2
title: 展台设计 · 初稿
status: 进行中
owner: 张三
participants:
  - 李四
  - 王五
due: 2026-11-28
deps:
  - w1
created: 2026-11-19
updated: 2026-11-20 09:30
---

# w2 展台设计 · 初稿

## 详情

三套方案，突出品牌主色。

## 日志

| 时间 | 事件 | 解决方案 |
| ---- | ---- | -------- |
| 2026-11-19 17:05 | 张三报价比上季度高 30% | 采购再找两家比价，设计先出草图 |
```

约定：

- 文件名 `w{编号} {事项名}.md`，标题变化时由工具重命名；事项 id：`w` + 数字，项目内唯一；依赖只能引用同项目的事项。
- 状态：未开始 / 进行中 / 等待反馈 / 已完成 / 已关闭 / 暂停。`item.add` 不传 status 时默认「进行中」（AI 补建的事项默认进行中）；只有用户明确说完成、或用户在界面把状态改成「已完成」才写「已完成」。
- 依赖未完成 → 事项被视为「被卡住」，驾驶舱与上下文都会提示。
- 日志的「事件」写前因与事实（承接哪条日志/事项、谁/何时/发生了什么），「解决方案」写处理、结果、下一步与关联（人/依赖/项目）。
- 一条日志对应一次有意义的变更，不是一条消息：同一天同一件事合并成一条；后来补充的细节用 `item.log.update` 改原条目，不重复追加。
- 写入只经过工具（`item.add` / `item.update` / `item.log.add` / `item.log.update`），工具负责建文件、重命名并刷新 README 索引；模型不手工造文件。
- 旧版（一个项目一个 `{项目名}.md`）仍可读取：第一次写入或点「迁移旧档案（单文件 → 文件夹）」时拆成 README + 事项文件；`item.add` 等写操作也会自动迁移。

### 日常工作（不属于任何项目的事项）

临时性的工作不硬塞进项目，也不为它造一个假项目，而是落在：

```
work/{部门}/{年}/日常工作/
├── 2026-11-20 10-02-27 临时：整理报销单.md
└── 2026-11-20 11-15-08 订会议室.md
```

- 一个事项一个文件，文件名前缀是添加时的日期 + 时分秒（`YYYY-MM-DD HH-MM-SS`），后面接事项名；事项 id 为 `d1`、`d2`…（日常工作目录内递增）。
- 内部结构与项目事项一致：frontmatter 字段 + `## 详情` + `## 日志` 表格；区别是 `uid: 0`、`scope: daily`，没有依赖和项目 README。

```markdown
---
schema: workos/v2
kind: item
scope: daily
uid: 0
item_id: d1
title: 临时：整理报销单
status: 进行中
owner: 我
participants:
  - 李四
due: 2026-11-25
deps:
created: 2026-11-20
updated: 2026-11-20 10:02
---

# d1 临时：整理报销单

## 详情

把 11 月发票贴好。

## 日志

| 时间 | 事件 | 解决方案 |
| ---- | ---- | -------- |
| 2026-11-20 10:06 | 财务说发票抬头错了 | 重开两张，明天上午前寄出 |
```

- 驾驶舱顶部「添加事项」打开同一个事项弹窗，多一个「所属项目」下拉框：选项目 = 普通项目事项；留空 = 日常工作。
- 日常工作事项在工作台的「日常工作」卡片里列出，可加入对话、看详情、改状态、记日志、编辑、删除。
- 工具约定：`item.add` / `item.update` / `item.log.add` / `item.log.update` / `item.delete` 不传 `uid`（或 `uid: 0`）时操作日常工作；`itemId` 用 `d1` 这样的编号。
- 自动归档的归属判断：一次性的、临时插入的、没有独立项目目标 / 节点 / 交付物的事 → 日常工作；有独立目标、交付物、节点、预算 / 客户、多人协作或需持续跟进 → 先搜索项目，找不到再问或建项目。不要为临时工作造项目，也不要把临时工作硬塞进无关项目。
- 个人汇报（不传 `uid`）把日常工作作为 `uid: 0 / 日常工作` 的一个桶汇总进去；项目汇报（传 `uid`）不包含日常工作。

## 日报 / 周报

汇报仍是 Markdown，按作用域分两处，文件名都是日期/区间：

- 个人汇报（汇总全部项目）：`data/日报/YYYY-MM-DD.md`、`data/周报/YYYY-MM-DD_YYYY-MM-DD.md`（含首尾日期）
- 项目汇报（只汇总一个项目）：`work/{部门}/{年}/项目/{项目名}/汇报/日报/YYYY-MM-DD.md`、`.../汇报/周报/YYYY-MM-DD_YYYY-MM-DD.md`

```markdown
---
schema: workos/v2
kind: report
scope: project          # personal（个人汇报）/ project（项目汇报）
project: WorkSelf 工作驾驶舱
uid: 1001
report_type: daily
start: 2026-11-19
end: 2026-11-19
generated_at: 2026-11-19 18:30
updated_at: 2026-11-19 18:30
source: manual
title: 2026-11-19 日报
---

# 2026-11-19 日报

- **生成时间**: 2026-11-19 18:30
- **汇报时段**: 2026-11-19
- **来源**: 手动生成

## 简介

一句话说清这段时间最重要的进展、卡点和下一步。

## 详细内容

按项目/事项组织：做了什么、结果、卡点、下一步。
```

约定：

- 时段：日报必须是单日；周报用闭区间 `start`/`end`（含首尾）。相对时段 `today` / `this_week` / `last_week` 在写入时由工具解析成具体日期。
- 生成时间：由写入工具自动记录，模型不编造；用户二次编辑只改简介/详细内容，`generated_at` 保留，`updated_at` 更新。
- 来源：`manual`（手动生成）或 `auto`（自动化任务）。
- 作用域：`workos_report_data` / `workos_report_save` 不传 `uid` = 个人汇报（汇总全部项目，写 `data/`）；传 `uid` = 项目汇报（只取该项目，写进该项目文件夹的 `汇报/`）。`scope` / `project` / `uid` 由工具写进 frontmatter，路径也算作用域兜底。
- 驾驶舱读取全部汇报，按 `generated_at` 倒序展示：工作台的「个人汇报」卡片只显示个人汇报，项目详情只显示该项目的汇报；汇报也进入全文索引，可被 `workos_search` 搜到。
- 助手生成汇报前先调 `workos_report_data` 取该时段的事实（日志、项目进展、在办事项），再调 `workos_report_save` 写回；没有日志就如实写「本时段没有日志记录」，不编造。
- 二次编辑只允许改 `data/日报`、`data/周报` 与项目文件夹 `汇报/日报`、`汇报/周报` 下的 `.md`，其他路径直接拒绝。

## 工作区 Agent（AGENTS.md）

初始化时在**工作区根目录**写入（已存在同名助手段时原地刷新为最新规则）：

```
<workspace>/AGENTS.md   ← 带 <!-- workos-agent:start --> ... <!-- workos-agent:end --> 标记
```

内容是以「我」为原型的助手设定：身份与语气、**档案结构（一个项目一个文件夹、README 主档、事项独立文件、日志写在事项文件里、只用工具写入）**、上下文展开流程、回答结构、每轮对话的自动归属与日志规则（前因/事件/结果/关联、合并去重）、新联系人先查名单问清资料再 `contact.add`（已有人用 `contact.update` / `contact.appendExperience`）、经验沉淀、删除确认。DSH 的 `dsh-agent-instructions` 自动把根目录到会话工作目录之间的 `AGENTS.md` 作为 agent 指令加载，所以该工作区的每个新会话都自动成为这个助手，无需选择 preset。已有 `AGENTS.md` 保留原内容，助手段追加在末尾；缺标记时下次打开会补上。

## 联系人

`data/workos/contacts.md`

```markdown
| id | 姓名 | 公司 | 部门 | 职位 | 电话 | 负责事项 | 打交道经验 | 备注 |
| -- | ---- | ---- | ---- | ---- | ---- | -------- | ---------- | ---- |
| c1 | 李四 | 某某集团 | 品牌科 | 设计师 | 138****xxxx | B2B设计 | 好说话，但排期紧时要提前三天催；交付前要彩排一次 | |
| c2 | 我 | | | 本人 | | | 工作方式、偏好与自我提醒见 data/个人信息.md | 系统用户本人 |
```

「打交道经验」只写**对人的认知和应对**，不写具体事件；事件进事项日志。旧版表头没有这一列，读取时为空，写入时自动补列。

初始化会在第一位放入「我」（系统用户本人），可编辑；新事项负责人默认「我」。已有档案在下次打开时补上「我」。

对话里出现档案中没有的人，助手先查名单、问清公司 / 部门 / 职位、关系、负责什么、联系方式与怎么打交道，用户回答后再用 `contact.add` 补进联系人；已在事项里当负责人 / 涉及人员的，先补联系人资料再校正事项，避免工具用空资料自动建档。已有的人用 `contact.update` 改资料、`contact.appendExperience` 记行为模式，不重复建、不编资料。

## 上下文展开（workos_context）

给 `uid`，可选 `itemId` / `logIndex` / `person`，返回：

- 项目：目标、状态、节点、背景、近期进展、复盘；
- 事项：全部字段、日志、依赖事项的当前状态（是否完成/卡住）；
- 人员：负责人 + 涉及人员的公司/职位/负责事项/**打交道经验**、`人脉关系.md` 中同名段落、他们手上其他在办事项（最多 5 条）；
- 同项目其他事项，供判断影响面；
- 项目 README、事项文件、依赖事项文件的相对路径与**完整路径**，便于直接定位。

AI 的回答由这些事实驱动；消息里的【工作上下文】只是索引，不是数据源。

## SQLite 索引

| 表 | 内容 |
|---|---|
| `doc` / `doc_fts` | 每份 Markdown + 中文二元组全文索引 |
| `project` | 项目目标、状态、进度、阻塞数 |
| `work_item` | 事项、负责人、涉及人员、依赖、日志数 |
| `item_log` | 每条日志（项目、事项、时间、事件、方案） |
| `contact` | 联系人资料与打交道经验 |
| `meta` | 同步摘要 |

同步：文件 hash 未变则跳过；结构化表全量重建；索引可随时删除。中文按重叠二元组切词，两字词可搜。

## 为什么不把真相放进 SQLite

1. 人与 AI 都要读：Markdown 可手改、可 diff、可备份。
2. 项目档案一半是散文（目标、复盘），数据库存了也要渲染回来。
3. 索引可以随时重建；真相不能。
